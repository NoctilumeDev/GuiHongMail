# M1–M6 连续运行合同 · 0.1

> **M0 附件；尚未授权执行。** 本文件定义一次授权的工作方式，不构成后台自动任务。授权后由实际运行的 Codex/Agent 依用户指定执行环境完成。

## 一次授权，自动串行到停机点

```
用户审定 M0 → 人明确发出 M1_START
    ↓
M1 基础 → 门禁闭合 → M2 邮箱 → 门禁闭合 → M3 SMTP
    ↓
M4 分类/完整产品 → 门禁闭合 → M5 有限故障反例
    ↓
M6 复验/工程候选 → 记录停止时间、资源清理与独立证据
    ↓
AWAITING_M7_HUMAN_REVIEW（必须停，等待用户）
```

除未获授权越界、不可自行修复的硬故障、外部资源/安全红线和明确环境阻断外，不因阶段切换、一个轻微可控失败、局部 CI 等待或需要继续复验而打断用户。M1→M6 由已批准的阶段合同足额授权。若 M0 未审定，唯一合法状态是 `WAITING_FOR_M0_APPROVAL`。

## Agent 必须区分的状态

`PLANNED` 不等于 `IMPLEMENTED`；`IMPLEMENTED` 不等于 `TESTED`；`LOCAL_PASS` 不等于 `EXACT_MAIN_PASS`；`TEST_PASS` 不等于 `PRODUCT_PASS`；`M6_ENGINEERING_CANDIDATE` 不等于 `M7_VISUAL_APPROVED`。现有能力、不可用能力和缺证据能力分别写入项目账册，不通过表述技巧越权。

所有阶段使用项目独立任务目录、分支与受控资源。对已批准范围内的修复可自动最小改动并重验，失败记录不可覆盖。可用信息不足时，降低行动权限、保留不确定性，而不是按猜测添加新微服务或改写已封存的标准。

## 计时与人力记录

记录 `run_id`、开始/结束 UTC ISO 时间、时区、初始/最终 SHA、环境 Profile（CPU、内存、Docker 预算）、Agent 模型/工具版本、M1–M6 各门的首次进入与最终闭合时刻。另记人工介入时间与原因、环境恢复时间、依赖下载时间、实际验收时间、发现/修复与原失败链接。没有数据写 `UNKNOWN`，不得推算虚假的 token、工时或效率倍数。

用户的评估问题是「在冻结 M0 后，Agent 可以多快独立完成一个具备真实协议/故障的有限单机邮箱？」；**工程退出以不变量和真实证据为准，不以时间为准。**

## 立即停工条件

1. 即将操作全局代理、系统网络、未知进程、其他项目存储、未授权公网邮箱或外部账户。
2. 核心事实被覆盖/丢失、BCC/附件越权、匿名 open relay、源数据/秘密将进入公开仓库，或任一不可接受的业务不变量无法在受控修复下闭合。
3. 资源超过冻结预算持续、清理归属不明、外部依赖不可使用或真实验证前提丢失。
4. 若继续需要重定义 M0 的目标、身份/权限、SMTP 成功含义、服务所有权、项目范围或 M7 视觉方向。

阻断状态至少写：exact SHA、触发前提、已完成范围、原始失败证据、为什么不能继续、剩余 owned 资源与安全处置、恢复入口。**禁止把 STOP 当作 M6 完成**。

## 到达 M6 后的停止要求

统一报告工程能力、证据范围、原始失败和已处置/未处置项；生成待人工评审的视觉清单，但**不进行审美精修**。不得为了等待用户而无期限保持本机服务/容器运行；先做 owned 资源清理与状态读回，用户按需按说明重新启动。
